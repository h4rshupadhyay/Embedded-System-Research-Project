# Candidate B: adversarial literature check

Checked 19 October 2026. Scope: the question in [RESEARCH_QUESTION_BRAINSTORM.md](./RESEARCH_QUESTION_BRAINSTORM.md#b-which-tests-expose-dsp-library-failures-that-output-comparisons-miss). This is literature and artifact screening; no new defect discovery, reproduction, implementation, or benchmark was performed.

## Verdict

**Do not claim a new testing method or a validated research gap. Retain only a conditional comparative empirical study.** Specification-driven valid call sequences, state-machine testing, metamorphic equivalences, numerical differential testing, and DSP-specific boundary selection already have direct precedents. Most seriously, MF++ already synthesizes equivalent API-call sequences from a manual specification and reduces failures; STITCH explicitly represents cross-call state and usage constraints. Their existence removes “contracts plus sequences” as a sufficient contribution. [MF++, ICST 2022](https://andreil.eu/papers/icst22.pdf); [STITCH, 2026 preprint](https://arxiv.org/abs/2602.18689).

The inspected sources do **not establish the answer** to the exact equal-cost, historical-DSP-defect comparison. That leaves an unverified evaluation question, not evidence of novelty. A useful result would explain when additional contract observations outperform strong existing generators and ordinary memory checking, across independent defect families. A positive result is not assured; a narrow replication or benchmark artifact may be the attainable contribution.

## Strongest novelty objection and surviving question

**Objection:** the proposed ingredients already exist, and the motivating memory failure might be caught simply by correctly sized allocations, guard pages, or sanitizers. CMSIS maintainers themselves already discuss stronger tests, fuzzing and shared-memory scenarios in the history-copy fix. [Official PR #245 discussion](https://github.com/ARM-software/CMSIS-DSP/pull/245). This makes “output comparisons miss something” a motivation, not a research contribution.

The remaining candidate should be stated narrowly:

> On independently reconstructed historical DSP-library defects, does adding explicitly documented state/buffer/call observations and legal schedule generation increase root-cause discovery at matched execution budgets, beyond official tests, numerical differential/metamorphic tests, and memory guards/sanitizers, and which defect families explain any increment?

Separate two factors: **generator** (signal values, sizes, legal schedules) and **oracle** (output, permitted state, protected memory). Give competing generators the same strong oracle, then ablate oracle additions. Otherwise improved detection could come entirely from adding a canary rather than from contract generation. Report wall time and library-call/sample budgets separately; charge reference computation, initialization, checking and reduction, and disclose manual contract-authoring effort. Match seeds, compiler options and backend. Hold out root-cause families from generator tuning; count one root cause once across affected APIs. These are proposed design requirements, not results.

Baselines must include unchanged official tests at the corresponding historical revision, official tests plus memory guards, legal randomized boundary/signal cases with ASan/UBSan where supported, independent numerical differential references, algebraic/domain boundary cases, and an MF++-style equivalent-sequence/state-machine generator. ASan explicitly targets out-of-bounds accesses and related memory errors; instrument the library as well as the harness, and document unsupported paths. [Clang ASan documentation](https://clang.llvm.org/docs/AddressSanitizer.html). A generic sequential fuzzer adapted to the same DSP contracts is essential before claiming a special DSP generator adds value.

This shortlist does not yet meet the requirement for diverse executable state/history defects across functions/backends. Recover exact parent/fix trees, contemporaneous documentation, compiler flags, preprocessed path, legal buffer formula, and expected buggy/fixed behavior before committing to a study.

A host scalar build cannot validate an MVE-specific defect. QEMU documents Cortex-M55 `mps3-an547`, and its Cortex-M55 model source specifies an FPU/full-MVE configuration, making a separate Helium-capable setup plausible; the existing M0 simulator remains insufficient. Pin an available QEMU version and verify the intended instruction path before counting it as executable. Emulated functional evidence cannot establish real-hardware timing or all memory-system behavior; hardware validation is needed for hardware-specific claims. [QEMU board documentation](https://qemu.readthedocs.io/en/master/system/arm/mps2.html); [QEMU Cortex-M55 source](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/tcg/cpu-v7m.c).

Legal contracts are decisive: Arm documents vector-buffer padding, architecture-specific API differences and permissible numerical differences. Guard the **allowed allocation**, not the logical signal end; a documented padded read is not a defect. Do not infer permitted aliasing or schedule changes from silence. [CMSIS overview](https://arm-software.github.io/CMSIS-DSP/main/). Q15 FIR specifies wide accumulation, truncation and saturation, so a wrapping FIR model is not a universal oracle. [Official Q15 source](https://raw.githubusercontent.com/ARM-software/CMSIS-DSP/main/Source/FilteringFunctions/arm_fir_q15.c).

## Kill criteria and search record

Stop the method claim if gains disappear with identical guards/oracles; if legal schedules cannot vary meaningfully; if historical pairs reduce to one family; or if decisive cases require unavailable execution paths. Reject precondition violations and count seeded mutants separately. A useful negative comparison is possible; publication value remains uncertain.
