## Recommendation

**The candidate I would investigate first is this method question: can the structure of exact FIR accumulation yield a provably safe, substantially cheaper search over partitions and schedules than generic search, while preserving useful compiled implementations?** This prioritization is a judgment based on the project's existing evidence, not demonstrated feasibility or a verified literature gap. The possible contribution is a structural search result or a demonstrated efficient method built on that result. It is not the range bound, two narrow partials, scheduling, an autotuner, or their mere combination.

**No substantial new gap is established yet.** The current project supplies a credible motivation and a working correctness/evidence framework. The next deliverable should be a short comparison of mathematical formulations and a hand-worked witness, before writing an optimizer or generating another measurement grid. If the comparison reveals only familiar optimizations in a new target setting, retain the existing empirical paper and choose a different research problem if stronger novelty is required. ## What is already proved locally

For one frozen full-int16 48-tap filter, two fixed coefficient groups admit exact int32 partial sums even though the conservative full-sum bound exceeds int32. Widening each partial before reduction preserves the one final floor-and-saturate quantizer. Corrected direct wins the two GCC10 comparisons; demand Hcub wins the two GCC15 comparisons. This is a stronger arithmetic control and an original observation about the artifact, not a novel accumulation principle. [Arithmetic contract and four-row result](fir-sharing-probe/explanation-check/claims.md), [join assessment](fir-post-join-research-assessment.md).

It does not identify the responsible compiler pass or predict the savings from eliminating those transfers. These are useful motivating observations; they establish no general performance law. [Accepted explanation and residual](fir-sharing-probe/explanation-check/final-decision.md).

The earlier held-out arithmetic selector, after the padded-library correction, chooses the modeled-energy winner in 77/108 groups with 5.25% mean and 51.83% worst overhead. Much failure is explained by established library/state/compiler behavior. Re-fitting that selector to the same cases would not independently validate a new insight. ## Two unproven hypotheses, in priority order

### H1 — A structural restriction makes exact partition/schedule search tractable

**Question:** For a clearly restricted family of direct FIR implementations, can coefficient-range certificates support a *sound dominance rule or sufficient search state* that removes partitions/schedules without removing the best member under an explicitly defined software cost model?

Start narrowly: unchanged coefficients and input domain; disjoint contiguous tap groups; one exact native-width accumulator per active group; exact wider reduction; one final quantizer; explicitly limited interleavings/output blocking and a stated storage model. The author must specify which of these restrictions are necessary, rather than quietly searching arbitrary arithmetic graphs. The frozen split is one feasible member, not an optimizer. [Existing fixed construction](fir-sharing-probe/explanation-check/claims.md).

A plausible object to investigate is whether a search state consisting of tap position, certified accumulated range and the set of live accumulator/reusable sample values suffices for a recurrence or dominance test. **This is a candidate, not a proposed theorem:** sample reuse, addresses, remaining coefficient uses, instruction alternatives and backend transformations may require more information. A pair of partial schedules with the same proposed state but different future legal costs immediately refutes sufficiency. A rule that prunes the optimum refutes soundness.

The new contribution would need to be the demonstrated structural result and resulting search advantage, or a carefully justified practical approximation with a new predictive finding. Merely replacing SQNR with an exactness predicate in an existing search, minimizing group count, using a standard contiguous-partition dynamic program or coefficient-bound bin packing, or adding a spill/register-pressure penalty to autotuning does not establish this. A method claim must name the advance beyond those routine constructions. The closest challenge is the software width-search and FIR blocking literature above, with generic integrated scheduling as a strong expressiveness control. [Ménard manuscript](https://www.researchgate.net/publication/220905057_DSP_Code_Generation_with_Optimized_Data_Word-Length_Selection), [SPIRAL FIR](https://spiral.ece.cmu.edu/pub-spiral/pubfile/fir.pdf), [Unison](https://arxiv.org/abs/1804.02452).

**Evidence that defeats or narrows H1:** an earlier equivalent recurrence/dominance rule; the candidate is only an obvious instantiation with no useful algorithmic advantage; legality or prefix safety fails; state size grows into effectively unrestricted enumeration; or the structural optimum has no useful relation to compiled cost. A model-level result can survive the last failure only as an honestly narrower result with independent value, not as a successful FIR performance optimizer.

### H2 — A specific sharing/recomputation rule predicts when graph sharing should be abandoned

**Question:** Within fixed exact transposed FIR state widths, can a stated rule choose which MCM intermediates to share, recompute or replace with native multiplies *before target benchmarking*, and reduce implementation-selection regret or search cost on unseen coefficient structures?

This must go beyond minimizing arithmetic counts or minimizing a generic peak-live-value count. A candidate rule would need to model the interaction of consumer order, width-dependent register occupancy, state updates and repeated uses well enough to make a checkable decision. Ordinary compiler backends already schedule for register pressure and spill virtual registers when required; those mechanisms are not new. [LLVM code-generation documentation](https://github.com/llvm/llvm-project/blob/main/llvm/docs/CodeGenerator.md). Neither Hcub's acknowledged objective boundary nor a hardware/software distinction establishes priority for a new rule. [Hcub](https://spiral.ece.cmu.edu/pubs/synth.pdf), [hardware joint optimization](https://www.mdpi.com/2079-9292/11/11/1721).

**Evidence that defeats or narrows H2:** the rule is equivalent to existing scheduling/common-subexpression/rematerialization heuristics; it cannot outperform pressure-aware scheduling of the same graph or equal-budget empirical search; it depends on observed costs of its test cases; or its benefits disappear against equally range-specialized direct implementations. A new graph that happens to beat Hcub on the original filter is a local implementation result, not sufficient method novelty.

H2 has greater overlap risk and a larger comparison burden. Treat it as an alternative if H1 yields no defensible question, not a second optimizer to implement now.

## Cheapest next evidence, before code

Produce a **one-page closest-method comparison**, with an attached tiny analytic example if needed, and a time limit of roughly one focused working day. This is the recommended next action, not work already performed here.

1. **Write H1 as a mathematical problem.** State inputs, permitted graph transformations, exactness requirement, cost model, candidate dominance/state rule, and the proposed property in one paragraph plus equations. Distinguish any theorem about the simplified model from a prediction about GCC output. If no concrete rule/property can be written, stop: “joint optimize everything” is not yet a research question.
2. **Challenge it against at most three closest methods first:** Ménard's software width/instruction search, SPIRAL's FIR decomposition/search, and Unison's integrated allocation/scheduling. Translate each into the same variables/constraints rather than comparing titles. For H2 instead prioritize Hcub, Rao/Lou and Unison. Follow only references that threaten the claimed distinction. Record precisely whether a method lacks an operation, can express it but searches inefficiently, or already supplies the supposed new rule. Full text needed for a decisive exclusion must be obtained or marked unresolved.
3. **Work one tiny symbolic instance by hand.** Enumerate a small admitted coefficient/group example and two legal schedules; record every prefix range, widening point, live value and symbolic instruction/memory cost. Then test whether the proposed rule preserves the best modeled schedule. An invented cost difference or nonseparable toy example is a discovery aid, not evidence of novelty or compiled speedup. Try actively to build a counterexample to the proposed state/dominance property.
4. **Write the strongest surviving contribution sentence and its defeat condition.** For example: “For restricted family F and model C, rule R preserves the optimum while reducing search by property P.” F, C, R and P must actually be specified and the property justified. If all that survives is “search familiar alternatives on Cortex-M0,” record a no-go for a new-method claim. If only full-text access is missing, record uncertainty rather than claiming a gap.

This is a low-cost decision gate, not a promise that one day establishes novelty. It may legitimately conclude that no worthwhile claim survives. The useful output is one specific claim worth testing, or a documented reason to stop that direction.

## Gates for investing in an implementation

| Gate | Evidence required to continue | Stop, revise or narrow when |
|---|---|---|
| Distinction | A technically explicit difference from the closest accessible methods; access limits separately recorded. | Difference is only target, language, exactness flag, familiar objective weights, or packaging. |
| Correctness/structure | Proof of the proposed rule for the restricted model, or an explicitly heuristic claim with a falsifiable prediction and meaningful baseline. | A counterexample breaks legality, pruning or claimed guarantee; repairing it eliminates the advantage. |
| Utility | Predeclared value criterion: e.g. lower search effort at matched solution quality, better solutions at equal budget, or lower held-out regret at a stated resource cost. | Benefit is only compared with a weak arithmetic heuristic, has been selected after seeing evaluation outcomes, or cannot justify implementation complexity. |
| Evaluation readiness | Frozen algorithm, baselines, workload split, budgets and accounting before new evaluation. | The existing development cases are being relabeled as independent validation or unfavorable cases excluded. |

An original *empirical insight* is another possible outcome: a compact, previously unestablished condition that predicts a consequential choice across new cases and survives matched causal controls. It need not be a new algorithm. “Compilers differ,” “fewer adds can lose,” or one new counterexample does not meet that stronger description given the inspected prior work. [Known locality/search precedent](https://spiral.ece.cmu.edu/pub-spiral/pubfile/fir.pdf), [current local boundary](fir-post-join-research-assessment.md).

## Fair evaluation if a claim survives

The following is a prospective protocol outline, not authorization or a reason to launch a campaign now.

- **Equal arithmetic information.** Freeze identical coefficients, signed input domain including −32768 where admitted, full streaming semantics and the one final quantizer. Give every representation the same range information. Prove every intermediate, including prefixes, products, shifts and reductions; output matching alone does not prove validity on the guaranteed domain. Preserve the current distinction between correctness and finite-stream performance evidence. [Existing evidence contract](fir-sharing-probe/explanation-check/claims.md).
- **Strong controls.** Include the best known certified direct strategy, known grouping/greedy alternatives, uniform-wide and fixed-split controls, appropriate tuned library builds including documented padding, ordinary transposition and Hcub, and equally budgeted search over the stated candidate family. H2 also needs the same graph with a competent pressure-aware schedule, unshared/native-MUL alternatives, and isolated sharing/scheduling/width ablations. Reuse the baseline corrections already learned. [Selection baseline correction](fir-selection-validation-findings.md).
- **Separate the contribution from its ingredients.** Compare range-only, schedule-only and joint decisions. If claiming safe pruning or optimality, compare with exhaustive enumeration for small instances and report only the proven family/model; timeout incumbents do not prove optimality. For an efficiency claim report search time, compilation/measurement budget, achieved cost and exclusions together.
- **Independent prediction.** Treat all existing filters, compilers and diagnosed examples as development evidence. Freeze the method before evaluating genuinely new coefficient structures, lengths, input guarantees and block/stream regimes. Include boundary cases where the full sum barely crosses native width, groups do/do not help, sharing is weak/strong, and register pressure changes. Count repeated conditions as repeated conditions, not independent applications. [Previous held-out design and limits](fir-selection-validation-findings.md).
- **Costs and causes.** Report cycles/instructions, reads/writes, state, stack, code size, and search overhead; name fixed-compiler and selectable-compiler questions separately. Check explanations with matched transformations and emitted code, without inferring that frame growth alone proves spilling. A method whose benefit is specific to a backend can still be studied, but its claim must be about that supported scope. [Accepted causal limits](fir-sharing-probe/explanation-check/final-decision.md).
- **Energy boundary.** Simulator event-weighted costs remain modeled CPU energy; hardware energy claims require a separately designed physical validation with appropriate uncertainty. The reused Cortex-M0 model's aggregate error is not a pairwise confidence bound for the new comparisons. [Primary model and validation](https://arxiv.org/html/2301.12806v1), [local measurement boundary](fir-sharing-probe/explanation-check/claims.md).

## Final decision for this research turn

My preferred candidate for investigation is **a specific structural rule for exact partition/schedule search, challenged on paper before implementation**. It is attractive because it uses the project's actual arithmetic and code-lifetime evidence while requiring a contribution beyond its known ingredients. Its tractability, originality and compiled benefit are all unproved. H2 is a higher-risk fallback, not an established gap.

This targeted search covered exact/bit-true FIR generation, software word-length search, partitioned multiplication/accumulation, MCM register objectives, FIR locality/autotuning, integrated scheduling/allocation and newer neighboring hardware work. It was not a systematic review; inaccessible sources and uncaught closer work remain possible. There is no novelty or publication guarantee. The existing empirical case study remains intact regardless of whether the proposed research question survives. [Current case-study recommendation](fir-next-step-after-explanation.md).
