# Deadline-constrained online FIR batching: gap assessment

20 October 2026. FIR only; simulator only; exact complete outputs. Literature assessment and proposed decision probe; no new implementation or experiments.

## Decision

**No-go as an established original-contribution topic. Conditional go for one small falsification probe only.** Energy-efficient batching subject to deadlines, online waiting-versus-serving, platform-dependent FIR implementation selection, and transition-aware DSP adaptation all have substantial prior art. The surviving question is narrower: whether *measured exact-integer FIR cost frontiers*, under a defensible arrival contract, produce a scheduling problem that existing batching policies handle materially poorly. That is an empirical hypothesis, not an identified unsolved problem. Absence of an exact-title duplicate is no evidence of novelty.

The prior screen in [fir-only-originality-audit.md](../fir-only-originality-audit.md) was too optimistic if read as establishing a gap. The existing [proposal](../professor-topic-proposal.md) supplies a strong correctness/measurement foundation, but neither an arrival model nor a demonstrated scheduling contribution.

## Define the actual problem before claiming a gap

The following is a **proposed model and analysis**, not a result attributed to the sources:

- One fixed coefficient vector and fixed numeric contract: `clip_int16(floor(sum(h[i]*x[n-i])/32768))`, exact wide sum before quantization. Emit all specified output indices exactly once, in order. State explicitly whether the stream includes a zero-input convolution tail; do not silently omit a required tail.
- Arrivals `r[n]` reveal samples in index order; deadlines initially `d[n]=r[n]+D`. Treat irregularity as delivery/availability of an indexed, normally sampled sequence. Physically nonuniform sampling changes the signal interpretation and needs an application justification.
- A batch consumes a contiguous pending prefix, uses only available samples plus canonical past history, and runs nonpreemptively on one fixed-speed processor. Specify whether outputs become visible incrementally or only when the call returns. Batch-end visibility is conservative; withholding genuinely available intermediate outputs must not manufacture a benefit.
- All kernels share logical history. Compatible implementations may use the same backing buffer; layout adapters, scratch space, ring wrapping and actual copy costs must be measured. Arm documents block state and post-block updates in its [CMSIS FIR interface](https://arm-software.github.io/CMSIS-DSP/latest/group__FIR.html). That does not imply a compulsory migration penalty when our compatible kernels switch. Avoid per-switch reinitialization or redundant shadow states.
- Minimize complete-stream modeled CPU energy subject to all deadlines and bounded RAM. Count dispatch, timers/polling, queue bookkeeping, history maintenance, calls, input/output movement and final partial blocks. State which acquisition costs are common. Without a validated sleep/wakeup model, report active CPU energy only; idle waiting is not automatically an energy saving.

**Guarantee boundary:** unrestricted arrivals can overload any finite processor. Zero misses on replay is not an online guarantee. Use a documented burst/rate arrival envelope and relative deadline, or a reservation scheme whose fallback is proved feasible for every admitted continuation. Proving only that currently queued jobs fit is insufficient: a nonpreemptive batch can block later arrivals. Offline-feasible traces alone do not establish that a causal controller can match clairvoyant feasibility. Start with common relative deadlines; adding unrelated urgent per-sample deadlines or background tasks solely to defeat a simple policy is unjustified without a real use case.

## Are there genuine competing regimes?

**Plausible, not demonstrated:** short isolated arrivals favor quick completion without waiting; dense bursts can amortize real per-call/history overhead across outputs. Larger batches can reduce energy per output while increasing absolute blocking time. A lower-energy but slower kernel versus a faster higher-energy kernel would create a stronger choice, *if measured*. Even when time and energy both fall with the same event counts, larger batches can still trade efficiency against waiting/blocking; do not assume an independent energy–time frontier exists.

**Weak/artificial regimes:** arbitrary migration constants, unsupported voltage/sleep states, deliberate slow baseline code, changing filter order/precision, dropping outputs, or assuming ordinary floating-point FFT convolution is bit-exact Q15. Include a frequency-domain method only after a complete exactness and cost argument. If real costs are approximately `setup + per_sample*b` and one kernel dominates at every size, the problem may reduce to ordinary batching with deadline flushes. A policy changing batch size is not by itself evidence of a new algorithm.

## Smallest decisive simulator probe (proposed only)

1. Use one existing nontrivial 128- or 256-tap filter and one fixed arithmetic admission contract. Compare the strongest admitted direct/folded and CMSIS kernels, with shared-history wrappers, for batches 1–16 (all residual sizes). Obtain complete-call time/energy and per-output release offsets; measure scheduler/adapter code separately. Check every output/history boundary against the reference, including alternating sizes and final short batches. First inspect dominance; stop if savings disappear after wrappers or only a contrived cost curve creates choices.
2. Use short streams of 16–32 outputs: sparse arrivals, dense bounded bursts, equal-mean/equal-count arrivals with different clustering, and arrivals immediately before/after dispatch timers. Choose one externally motivated bounded arrival envelope and sweep its deadline around the *measured* feasibility boundary. These are mechanism tests, not a dataset claiming application prevalence.
3. Compute a **clairvoyant offline optimum** over the same menu, FIFO order, memory limit and output-release semantics, with no fictitious switching cost. For batch-end visibility and state-independent active costs, enumerate contiguous partitions/kernel choices; for a fixed sequence, earliest starts `s=max(previous_finish,r[last])` suffice for feasibility. Maintain nondominated `(finish_time,total_energy)` labels per processed prefix; one cheapest-energy label alone is unsafe. Check all batch deadlines. If idle/wakeup cost or layout state matters, expand the state/model rather than using this simplified oracle. First cross-check tiny instances by exhaustive enumeration.
4. Compare (a) immediate strongest legal batch1; (b) best fixed kernel/batch cap with deadline-triggered partial flush and tuned timeout; (c) largest currently available feasible prefix; (d) cheapest measured feasible prefix/kernel with exact residual packing; (e) latest-safe-dispatch batching with a proved fallback reservation. Tune on separate arrival families; give every baseline the same cost table and safety mechanism. Add a known-arrivals rolling-horizon comparator only as explicitly noncausal diagnostic, not a deployable competitor. Compare to offline energy only on schedules meeting every deadline; separately report infeasible traces, misses, maximum lateness and queue/RAM peaks.

**Decision gate:** proceed beyond this probe only if a defensible workload yields repeatable headroom over the strongest simple policies after controller costs, and a specific structural reason or safety/optimality result survives comparison with serial-batching and online-service literature. An offline advantage alone proves opportunity, not an attainable online contribution. If “largest safe batch + profiled kernel” nearly matches offline, or benefit requires invented overheads, stop. At present this direction offers a possible reproducible systems case study, with no substantiated meaningful unsolved FIR scheduling gap.
