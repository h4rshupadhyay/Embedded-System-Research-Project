# Gap screen: exact fixed-coefficient FIR software generation

20 October 2026. FIR only; scalar MCU; simulator only. Read the proposal, next-direction screen and current novelty audit. No optimizer or target experiment was implemented; existing numerical results were not rerun.

## Recommendation

**No-go as a presently justified new algorithm topic.** A generator combining coefficient sharing, exact ranges, symmetry, scheduling and state costs would be useful engineering, but this screen does not establish a substantive unresolved algorithmic gap. Most ingredients, and several important combinations, are already solved. “Hardware work optimizes area, ours optimizes MCU cycles” is insufficient novelty. Keep at most a small falsification probe before committing to this direction; do not build the optimizer first.

A narrower unresolved *candidate question*, not a novelty claim, is whether a FIR-specific representation can expose a provable advantage over the established pipeline of adder-graph construction, exact width analysis and machine scheduling when sharing crosses sample times. An actual contribution would need a new result or optimization mechanism, plus evidence that existing approaches cannot express/recover it. A new cost table, solver formulation or combination of existing passes alone would not meet that test.

## Precise question and hidden structural issue

For fixed signed integer coefficients `h`, guaranteed integer input domain `[a,b]`, zero initial history and arbitrary input sequences in that domain, minimize complete-stream target cost while preserving

`y[n] = clip_int16(floor(sum_i h[i]*x[n-i] / 32768))`.

Coefficients and the final quantizer stay fixed. Intermediate truncation, saturation or wrapping cannot silently replace exact integer arithmetic. Candidate choices include direct/folded/transposed forms, SCM/MCM graphs, bounded recomputation versus sharing, instruction scheduling, register assignment and block/state organization. Charge input/output, retained state, spill traffic, calls, code size and short final blocks.

**Important deduction:** ordinary direct FIR products use *different delayed inputs*. MCM sharing applies to several constants times the *same* input. It therefore naturally appears in transposed FIR or input-centric blocked execution, not by applying an MCM graph independently to one direct dot product. Symmetry folding uses sums of different sample pairs, also generally different operands. Combining symmetry with MCM is consequently a genuine representation choice, not automatically multiplicative savings. The MCM definition and FIR applicability are explicit in [Voronenko–Püschel, §§1–2](https://spiral.ece.cmu.edu/pubs/synth.pdf); the implications here are our deduction.

## Smallest decisive probe, before implementation

1. **Analytical gate.** For every proposed graph node write its exact integer linear form in distinct input samples: `v=sum_j c_j*x[n-j]`. Its exact box-domain endpoints are `L=sum_j min(c_j*a,c_j*b)` and `U=sum_j max(c_j*a,c_j*b)`. Combine equal-sample coefficients first: independent interval propagation can overestimate correlated MCM values. For `v=c*x`, the endpoint proof is immediate. Certify shifted operands, pre-adds, accumulations and persistent transposed state, not just final products. This is elementary linear range analysis, not a new theorem. [Official FIR range rules](https://www.mathworks.com/help/dsp/ug/fixed-point-precision-rules-for-avoiding-overflow-in-fir-filters.html) supply the established foundation.
2. Count native-word operations and persistent storage for **one existing application filter**, one nonsymmetric control, and a tiny illustrative coefficient set. Obtain existing Hcub/SCM graphs; preserve coefficients. For a straightforward transposed realization, count each of its `N-1` persistent partial sums at its certified width. Unlike direct input history, these are accumulated values; do not assume int16 storage. A RAM-resident unblocked implementation normally loads/stores those states each sample; blocking/register retention can change that count, so it is not a universal lower bound.
3. Compute an *optimistic* target cost for each proposed realization, omitting spills/control and using legal minimum instruction costs. If even this exceeds a strong measured direct/folded baseline, reject that realization without building a generator. The bound must be justified for the specified realization; graph rewrites can invalidate naive operation-count bounds. Pin actual multiplier latency: do not assume all Cortex-M0 implementations have the same multiplier.
4. Only if headroom remains, hand-adapt a few existing graphs/schedules into exact kernels (not a new optimizer), compile and simulate complete streams. Compare fixed graph then scheduling, versus alternative graphs, versus simple recomputation. Use small exhaustive-domain checks plus wider adversarial/random reference checks and range certificates. Determine whether the whole alleged gain is ordinary backend scheduling, needless baseline width, state organization or known graph selection.

**Stop/go rule:** no go if the best result merely ports MCM to C, adds range proofs, adjusts spill weights, or discovers state traffic erases savings. A go requires a reproducible counterexample where established strong approaches miss an opportunity for a specified structural reason, followed by a genuinely new remedy/theoretical result. Beating greedy Hcub or one compiler alone is insufficient.

## Baselines, feasibility and risks

Use the strongest valid existing direct/folded kernels; CMSIS standard and fast Q15 with documented unrolling and odd-length padding; compile-time coefficient-specialized direct code; per-constant CSD/optimal SCM; Hcub/RAG-n graphs; exact full-precision width-aware MCM graphs; and direct/transposed or blocked state organizations. Hold the graph fixed when attributing schedule gains. [Official CMSIS FIR contracts and state layout](https://arm-software.github.io/CMSIS-DSP/v1.14.4/group__FIR.html) are essential controls. A general combinatorial backend such as Unison is a relevant small-kernel quality control if compatible; a Thumb-2 result is not automatically a Cortex-M0 result.

The existing simulator fixture makes a bounded probe feasible without a guide or physical board. Time availability does not resolve the novelty risk. Major risks are missing older compiler/DSP synthesis literature, confusing hardware pipeline registers with CPU live registers, code-size growth, undefined signed shifts/overflow in generated C, and optimizing arithmetic while increasing streaming memory traffic. Report verified instruction/timing-model results first; any energy remains a model estimate. **Recommendation: do not select this as the new original-contribution paper yet; retain it only as a falsifiable, inexpensive screen. Novelty is not certified.**

Temporal-contract boundary: adding a guarantee such as `abs(x[n]-x[n-1])<=D` changes the feasible input set and may tighten the linear-form ranges above, but is not automatically a new direction. The coordinating research screen identified Chang/Jen's [1998 differential-input FIR paper](https://dihana.cps.unizar.es/proceedings/ICASSP/1998/pdf/author/ic982260.pdf) and [2017 slope-bound verification case studies](https://www.sciencedirect.com/science/article/abs/pii/S1477842417300246) as direct predecessor leads. This agent's fetches failed, so their technical details are **coordinator-reported leads, not independently inspected evidence here**. Neither differencing nor adding slope bounds should be promoted as novel without that follow-up.
